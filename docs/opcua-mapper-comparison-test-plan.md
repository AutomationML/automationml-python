# AutomationML / OPC UA mapper comparison test plan

Status: implemented release-candidate acceptance plan  
Date: 2026-08-17  
Python profile under test: `strict-implicit-v1`  
Unmodified XSLT baseline:
[`AutomationML/AML-UA-XSLT@e38653c`](https://github.com/AutomationML/AML-UA-XSLT/tree/e38653c1bc58ffc658595093e0a2d163a7ecebf7)

## 1. Purpose and claim

This plan is designed to support a narrow, defensible claim:

> On a published corpus with implementation-independent conformance and
> semantic oracles, the Python mapper correctly handles more AutomationML/OPC
> UA conversion and roundtrip cases than the unmodified working-group XSLT,
> without embedded source AML or mapper-private ordering/identity metadata.

It is not designed to prove that Python is universally superior to XSLT, or
that the current Python subset implements all of CAEX or OPC UA. Unsupported
features count honestly as unsupported until their paired forward and reverse
rules pass.

The unit of comparison is a **manifest test case**, not a pytest function,
parameter, assertion, or randomized example. This prevents either
implementation from winning by splitting one behavior into many assertions.

## 2. Systems under comparison

| ID | System | Headline score | Purpose |
| --- | --- | --- | --- |
| `PY-STRICT` | Current typed Python forward/reverse profile | Yes | Candidate solution |
| `XSLT-RAW` | Exact upstream XSLTs at commit `e38653c`, executed without local patches or output repair | Yes | Original solution requested for comparison |
| `XSLT-RUNNER` | Exact upstream XSLTs plus its published `UnitTests/AML2UA.py` cleanup/CDATA/timestamp steps | Appendix | Shows whether the repository's own post-processing changes an outcome |
| `XSLT-PATCHED` | Our locally corrected XSLT | No | Regression/reference engine only |

The primary XSLT forward entry point is `AML2Nodeset.xslt`. The documented
reverse entry point is `Nodeset2AML.xslt`; `Nodeset2AML_V2.xslt` is reported as
a secondary upstream experiment, not selected opportunistically per case.

All engines use the same SaxonC version and process limits. The unmodified
baseline is vendored with its MIT licence, commit ID, and SHA-256 hashes so CI
does not depend on live GitHub state. The baseline harness may capture output
and errors, but may not rewrite its XML.

- 15 larger `TestData_AML` application/library examples;

- two reverse XSLTs; and
- `UnitTests/AML2UA.py`, which regenerates files and normalizes output but has

The SDK currently carries 9 of the upstream AML unit inputs and has focused
tests for the first five Python-supported fixtures, datatype canonicalization,
DefaultValue/Unit, native role references, OPC-UA-authored NodeIds, NodeSet

The first task is to import the complete upstream corpus unchanged. Existing
upstream NodeSet snapshots are **inputs and historical evidence**, not semantic
goldens: most were generated by the implementation being evaluated.

## 4. Case manifest and outcomes

Every case is declared before implementation work in a versioned manifest. A
representative record is:

```json
{
  "id": "AML-ATTR-DEFAULT-002",
  "title": "actual and default value remain distinct",
  "direction": "aml_to_ua_to_aml",
  "profile": "strict-implicit-v1",
  "severity": "must",
  "source": "fixtures/aml/attribute_actual_and_default.aml",
  "equivalence": "exact",
  "oracles": [
    "caex_xsd",
    "nodeset_xsd",
    "nodeset_semantics",
    "expected_graph",
    "canonical_aml"
  ],
  "forbidden": ["embedded_aml", "shadow_roundtrip_metadata"]
}
```

Allowed case results are:

| Result | Meaning | Counts as pass |
| --- | --- | --- |
| `PASS` | All required oracles pass exactly | Yes |
| `CANONICAL_PASS` | A predeclared canonicalization occurs and all oracles pass | Yes |
| `EXPECTED_REJECTION` | A negative/ambiguous input is rejected with the required diagnostic class | Yes, negative cases only |
| `FAIL` | The engine returns a wrong, invalid, lossy, or nondeterministic result | No |
| `UNSUPPORTED` | The engine explicitly lacks a mandatory feature | No |
| `CRASH` | Unhandled processor/runtime error | No |
| `INVALID_FIXTURE` | The input violates its declared preconditions | Excluded and fixed; never credited |

Canonicalization must be declared in the manifest before execution. A
difference discovered after looking at an implementation's output cannot be
retroactively called canonical.

## 5. Independent oracle stack

No single oracle is sufficient. In particular, UANodeSet XSD validation cannot
detect malformed NodeId strings, unresolved aliases, incorrect reference
semantics, or information loss.

### 5.1 Input oracle

1. Parse securely with DTD/entity expansion disabled.
2. Validate against the pinned CAEX 3.0 or declared legacy CAEX schema.
3. Validate AutomationML references, IDs, link partners, and class paths.
4. Reject a fixture whose validity declaration is wrong.

### 5.2 Forward AML-to-OPC-UA oracle

1. Transformation completes without post-output repair.
2. Output is well-formed NodeSet2 XML.
3. Output validates against the official pinned UANodeSet XSD.
4. All NodeIds, aliases, BrowseNames, DataTypes, parents, and references are
   syntactically valid and uniquely resolvable.
5. The expanded graph contains the expected NodeClasses, values, types,
   references, cardinalities, and model dependencies.
6. Strict cases contain no embedded AML or AML-only roundtrip shadows.
7. A second run with fixed inputs is semantically and byte deterministic.

### 5.3 Reverse OPC-UA-to-AML oracle

1. Input NodeSet passes the same structural/semantic checks.
2. Reverse output is well-formed, schema-valid CAEX.
3. The canonical CAEX Pydantic model equals the independently authored expected
   model using `RoundTripDifference` paths.
4. The result does not depend on generated NodeId layouts, XML ordering,
   namespace prefixes, alias spelling, or an embedded AML source.

### 5.4 Roundtrip oracles

- AML-origin: `AML -> UA -> AML` equals the declared exact or canonical AML
  semantics.
- OPC-UA-origin: `UA -> AML -> UA -> AML` has a stable AutomationML semantic
  projection.
- A roundtrip does not pass merely because the original source was embedded.
- Unsupported ambiguity must fail closed instead of silently choosing an
  undocumented interpretation.

### 5.5 Independent consumer oracle

For release candidates, import the generated NodeSet into `asyncua` after its
required base/companion NodeSets. Browse the expected nodes, read values and
references, and export/reimport the address space. Where practical, also run
an official UA ModelCompiler compile/import check. This oracle is intentionally
outside our XML and Pydantic implementations.

#### A note on `REG-DETERMINISM-001` and calendar coincidence

This case requires the caller-selected publication date
`2026-08-17T00:00:00Z`. The unmodified upstream stylesheet has no
`publication-date` parameter and stamps the current timestamp, which is the
defect the case exists to record. `XSLT-RAW` therefore fails it, correctly.

`XSLT-RUNNER` applies the official upstream runner's post-processing, and that
runner normalizes only the *time* portion of the stamp
(`T[0-9:]+Z` becomes `T00:00:00Z`); it does not select the date. On
2026-08-17 — the day the original evidence was frozen — the normalized stamp
therefore equalled the required date by coincidence, and the case was recorded
as a `PASS` for an engine that demonstrably cannot honor a caller-selected
date. On any other day it fails, which is the accurate result and what the
current evidence records.

The required date is fixed and in the past, so the coincidence cannot recur.
The case needs no change; it is documented here so that a future reader does
not mistake the corrected `FAIL` for a regression, and does not re-freeze
evidence on a day that reintroduces the false pass. `XSLT-PATCHED` passes this
case legitimately: accepting a caller-selected publication date is one of the
documented patches (see `evaluation/resources/xslt/PATCHES.md`).

## 9. Negative, ambiguity, and security cases

Every negative case requires a typed diagnostic category and a useful path or
NodeId. Merely throwing any exception is not a pass.

1. Duplicate NodeIds.
2. Invalid NodeId syntax and unresolved alias.
3. Reference to a missing document-local node.
4. Multiple competing TypeDefinitions.
5. Broken or cyclic class ancestry.
6. Component graph that is not a CAEX tree.
7. Variable missing DataType or object carrying Variable fields.
8. DefaultValue Property whose DataType differs from its owner.
9. Ambiguous role interpretation outside the profile default.
10. Parallel InternalLinks which collapse to one native edge.
11. Unknown datatype or invalid scalar lexical value.
12. DTD/entity input and external-resource resolution attempt.

## 10. Metamorphic and generated tests

Metamorphic tests prove that the converter consumes graph semantics rather than
incidental XML syntax. Each family is one scored gate with many deterministic
seeds:

1. Node and reference ordering permutations.
2. Namespace-prefix and namespace-index permutations.
3. Alias versus expanded-NodeId substitution.
4. Arbitrary document NodeId replacement.
5. XML indentation and irrelevant whitespace changes.
6. Repeated conversion determinism.
7. `AML -> UA -> AML -> UA -> AML` idempotence.
8. `UA -> AML -> UA -> AML` idempotence.

After the hand-authored corpus is green, Hypothesis generates valid documents
within the declared supported profile. CI runs at least 200 deterministic
examples per family; nightly tests run at least 2,000. Generated examples are
shrunk to a minimal permanent fixture when they find a defect. Random examples
do not count as thousands of headline cases.

All eight implemented Hypothesis families pass 200 deterministic examples in
the default test run (1,600 generated examples in total). The environment
variable `AML_HYPOTHESIS_EXAMPLES=2000` selects the planned nightly depth.

## 11. Interoperability and scale gates

### Interoperability

1. Import minimal generated model into asyncua and browse expected nodes.
2. Import a typed attribute/class-library model and read values/types.
3. Import a role/link model after loading required companion NodeSets.
4. Export from asyncua, re-import into the Pydantic model, and verify stable AML
   semantic projection.

All four cases pass with asyncua 2.0.1 and the pinned AutomationML companion
NodeSet. This run also found and forced fixes for missing inverse hierarchy
edges and dangling Part 19 dictionary targets.

### Scale and performance

1. 1,000 nodes / 5,000 references.
2. 10,000 nodes / 50,000 references.
3. Deep hierarchy at the supported CAEX depth/resource limit.

Report cold and warm wall time, peak memory, output bytes, and determinism. The
XSLT stylesheet may be precompiled for the warm comparison. Performance is
reported separately and cannot compensate for semantic failures.

The executed Windows release measurement produced 1,000 nodes / 5,939
references and 10,000 nodes / 59,939 references. The strict mapper was byte
deterministic and semantically roundtripped both graphs. At 10k nodes the warm
forward time was about 3.9 s, reverse was about 5.0 s, peak process RSS was
about 267 MiB, and output size was about 8.9 MiB. Depth 64 also passed. Exact
environment and unrounded values are in `docs/reports/opcua-scale/`.

## 12. Scoring and credibility gates

The report contains category scores and a total mandatory score:

```text
System       Forward   AML roundtrip   UA roundtrip   Negative   Interop   Total
PY-STRICT       x/y          x/y            x/y          x/y       x/y      x/y
XSLT-RAW        x/y          x/y            x/y          x/y       x/y      x/y
```

A public “better than the original XSLT” claim requires all of the following:

1. `PY-STRICT` passes 100% of critical validity, security, and no-silent-loss
   cases.
2. It has no critical regression on an upstream feature both systems claim.
3. It passes at least 20 more distinct mandatory semantic cases and at least 15
   percentage points more of the mandatory corpus than `XSLT-RAW`.
4. Every feature counted as supported passes both its forward and reverse gate.
5. Every strict roundtrip passes with source embedding disabled and forbidden
   shadow metadata absent.
6. All eight metamorphic families and all applicable asyncua cases pass.
7. All known-defect output mutants are rejected, demonstrating oracle
   sensitivity.
8. Results are reproducible on Windows and Linux from the pinned manifest.

Raw counts are accompanied by the complete result matrix. Failures,
unsupported cases, exclusions, and canonical differences are never hidden in
one aggregate percentage.

Gates 1-7 are green in the checked-in evidence. Gate 8 is configured as a
dedicated Windows/Linux GitHub Actions job; local evidence in this worktree is
Windows only until that workflow runs on the remote repository.

## 13. Sociotechnical review

Before a new case becomes a release oracle:

- an AutomationML reviewer confirms the expected CAEX semantics;
- an OPC UA reviewer confirms the expected graph and standard references;
- the case cites the applicable CAEX and OPC UA/AML clauses;
- any implicit/canonical choice is added to the mapping-profile document; and
- expected results are reviewed without copying either mapper's output.

The technical fixtures and expected projections are implemented. Independent
AutomationML and OPC UA expert signatures are intentionally still pending and
must not be inferred from the automated score; the review form is
`docs/opcua-mapping-review-checklist.md`.

The manifest and first red baseline report should be frozen before implementing
the currently deferred InternalLink, constraint, role-payload, mirror, and
facet rules. This reduces the risk of designing only tests that our mapper
already passes.

## 14. Implementation phases

### Phase 0 — comparison harness

- Vendor and hash the unmodified upstream baseline.
- Define the JSON manifest and Pydantic result schema.
- Implement raw XSLT, upstream-runner, Python, and patched-reference adapters.
- Emit machine-readable JSON/JUnit and a Markdown capability matrix.

### Phase 1 — inherited and defect corpus

- Import all 15 upstream unit inputs and 15 larger AML samples.
- Add the 12 minimal known-defect regressions and their output mutants.
- Establish the honest initial red/green score before expanding Python support.

### Phase 2 — paired semantic features

- Complete datatype/value/default/unit and dictionary cases.
- Implement constraints from red tests.
- Implement native InternalLinks and canonical reverse behavior from red tests.
- Implement role payload/MappingObject, mirror, and facet cases in that order.

### Phase 3 — OPC-UA-origin and metamorphic corpus

- Add all 16 authored NodeSets.
- Run identity, alias, namespace, and ordering permutations.
- Add structured ambiguity diagnostics.

### Phase 4 — interoperability and publication

- Add asyncua and optional ModelCompiler CI jobs.
- Run scale/performance measurements.
- Obtain AML and OPC UA expert sign-off.
- Publish the manifest, fixtures, full matrix, environment lock, and report.

Phases 0-3 and the automated parts of Phase 4 are complete. Remaining release
governance work is external AML/OPC UA expert sign-off and one remote CI run on
both operating systems. The optional UA ModelCompiler check remains an
additional independent consumer gate, not a prerequisite for the current
asyncua-backed claim.
